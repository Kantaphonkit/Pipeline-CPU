Data hazards

Forwarding: two distances, one priority rule

A producer whose destination is x0 wrote nothing, so it is never forwarded. Otherwise x0 would read non-zero for exactly one instruction.

The two hazards forwarding cannot fix

One cycle for a load-use, two for a taken branch

A redirect always overrides a stall: the instruction that raised the stall is being killed anyway, so waiting for it would deadlock the redirect.

Bonus A — branch prediction

64 two-bit counters, and an honest cost table

What it costs, by outcome

PredictionOutcomeBubblesWhy
not takennot taken0the fall-through was already being fetched
takentaken1the ID redirect kills one instruction
not takentaken2EX redirect kills ID and IF
takennot taken2wrong target fetched, then re-fetch the fall-through

Where each step happens

Lookup — IFindexed by the fetch PC, in parallel with the instruction fetch
Carry — IF/IDthe counter state travels with the instruction
Act — IDredirect to PC + immB, the same 1-bubble path jal uses
Resolve — EXcompare against the real outcome; flush 2 on a mispredict
Update — EXsaturating increment or decrement

There is no target buffer. The target is PC + immB, which ID already computes. That saves a tagged CAM and costs one bubble on a correct taken prediction.

Bonus B — interrupts

The trap point is EX, so mepc is always a real PC

ecall — synchronous

mcause = 11. mepc points at the ecall, which has not completed. The handler must add 4 before mret, or the ecall re-executes forever.

Interrupt — asynchronous

mcause = 0x8000000B. mepc points at an instruction that never executed. The handler must not add 4. mret re-runs it.

Level, not pulse

irq is qualified by mstatus.MIE and mie.MEIE. A request raised inside the handler is held, not lost, and taken as soon as mret restores MIE.

That asymmetry, ecall advances mepc and an interrupt must not, is the single most common trap-handling bug. We call it out rather than bury it.

Performance

The same three programs finish in 6,799 cycles instead of 9,003

Reading both charts

Forwarding helps most where dependencies are tight. fib gains 1.65x because each loop iteration consumes the previous result almost immediately. bloop gains least, and its load-use stall count is zero even with forwarding on, so there was nothing for the bypass to save.

The predictor can only win on taken branches. A correct not-taken prediction already cost nothing. bloop was written to defeat a 2-bit counter, alternating taken and not-taken every iteration, and the 400-cycle loss matches the arithmetic exactly.

Slide 2 promised performance measured against a baseline rather than quoted in isolation. This is that measurement, for both bonus features.

The last row is the interesting one

Training the predictor with the inverted outcome collapses accuracy. fib falls from 93.4 % to 3.3 %, and bloop costs another 438 cycles.

Yet every program still passes its byte-exact trace diff.

That is the right answer. The predictor only changes when instructions are fetched, never what they compute. Correctness rests entirely on the EX-stage resolution and flush, and the trace diff should be blind to a misprediction rate.

A testbench is not trusted until it has been shown to fail against a deliberately broken copy of the module it checks.
